# Handoff — Provision GitHub Packages npm auth via bootstrap user init step

**Execute from:** the `~/bootstrap` workspace, as user `luke` on the broadminde1 host (linux). You are configuring host-level user tooling, not any app repo.

## Why (context)

A new standalone repo `~/portal` (portal web shell) consumes the private npm package `@broadminde-org/frontend` from GitHub Packages (`npm.pkg.github.com`) as an *external consumer* (the ee monorepo gets the same code via git submodule instead, and must stay that way). npm install currently has **no working auth anywhere** on this host:

- No `~/.npmrc` exists.
- No `GITHUB_PACKAGES_TOKEN` in any `.env` (ee's checked; none).
- ee's project-level `.npmrc` files carry no auth (only `engine-strict`/`workspaces=false`).
- The `gh` CLI is authenticated as user `Luke-Williams9` with a fine-grained PAT (retrievable via `gh auth token` — **never print or commit it**). Whether that PAT has `read:packages` on broadminde-org is **unverified** — checking this is part of the task.

Side benefit: ee apps `sancus` and `fintek` set `workspaces=false` in their frontend `.npmrc`, i.e. they already install `@broadminde-org/frontend` from the registry with no auth configured — a user-level token repairs them too. The `frontend-shared-access` rule ("no Packages tokens in ee") applies to the ee repo's files, not to host-level user config.

## Task

Add a **user-mode** init.d step under `~/bootstrap/user/init.d/` that configures host-wide npm auth for GitHub Packages — either by extending the existing `99-go-shared` step or adding a new numbered step.

### Conventions (mandatory)

Load the **`init-d` skill** first (`/home/luke/.kilo/skills/init-d/SKILL.md`) and follow it: numbered drop-in, `set -euo pipefail`, idempotent, non-interactive, fail loudly, parameters from bootstrap's `.env`, secrets never committed.

### Design (decided — implement this)

- **Token source:** `GITHUB_PACKAGES_TOKEN` in bootstrap's `.env` (gitignored). It's an external secret — it cannot be generated by the step; the user creates the PAT manually. Document the variable in bootstrap's `.env.example` with a comment: needs `read:packages` on broadminde-org.
- **Auth mechanism (source of truth):** **user-level `~/.npmrc`**. Manage exactly these keys, creating the file if absent and preserving any unrelated existing content:
  ```
  @broadminde-org:registry=https://npm.pkg.github.com
  //npm.pkg.github.com/:_authToken=<token>
  ```
  `chmod 600 ~/.npmrc`. Rationale: env-var approaches (`~/.profile` export, direnv) fail in non-login shells, GUI-launched processes, and sandboxed agent sessions; user-level `.npmrc` is read by every npm invocation as this user.
- **Gotcha that shapes this design:** project-level `.npmrc` overrides user-level. A committed project `.npmrc` with `_authToken=${GITHUB_PACKAGES_TOKEN}` would override working user-level auth with an *empty* token whenever the env var is unset → 401. That's why auth lives only in `~/.npmrc`; project `.npmrc` files carry only the registry mapping. (Portal's plan is already aligned to this.)
- **Missing-token policy:** if `GITHUB_PACKAGES_TOKEN` is absent from `.env`, print loud skip instructions (how to create the PAT, where to put it) and exit 0 — do not break full bootstrap runs. If the token is present but verification fails (401), exit non-zero.
- **Token hygiene:** no `set -x` around token handling, never echo it, umask/chmod so any file containing it is 600.
- **Do not** modify ee, portal, go-shared, or frontend-shared. Do not add the token to any git-tracked file. Do not change the go-shared/frontend-shared SSH wiring.

### Decide at execution time (either is acceptable — report your choice)

**Extend `user/init.d/99-go-shared` vs. add a new step.** Read `user/init.d/99-go-shared/run.sh` first: that step already owns "access to broadminde-org shared artifacts" (it manages the go-shared *and* frontend-shared git deploy-key paths). If npm registry auth fits cohesively, extend it; if it would muddy the step, add a new numbered step (leave numbering gaps per the init-d skill).

### Verification (the step itself must run these, and you must run them manually after)

1. Token validity: `npm view @broadminde-org/frontend version` — must print a version. 401 means the PAT lacks `read:packages`: report back to the user that a fine-grained PAT with packages:read on broadminde-org must be created and placed in bootstrap's `.env`.
2. Env-independence: `env -i HOME="$HOME" PATH="/usr/bin:/bin:/usr/local/bin" npm view @broadminde-org/frontend version` — must succeed, proving no reliance on exported env vars.
3. Idempotency: run the step twice; second run is a clean no-op.
4. `grep -c authToken ~/.npmrc` is 1 and file perms are 600.

### Acceptance criteria

- [ ] `npm view @broadminde-org/frontend version` works in a fresh env (`env -i` test) as user luke
- [ ] Step is idempotent, non-interactive, follows init-d conventions
- [ ] `.env.example` documents `GITHUB_PACKAGES_TOKEN`
- [ ] Token never appears in stdout, logs, or any git-tracked file
- [ ] Final report states: step number/name chosen, and whether the existing gh PAT had sufficient scope or a new PAT is required from the user
